# 보안 한계 및 기관 승인 절차

## 1. 설계상 보호 조치

| 구분 | 조치 |
|---|---|
| 개인정보 수집 | 이름·연락처·주소·생년월일·주민/외국인등록번호·여권번호·건강정보 입력 칸 없음. 센터는 점검 코드(시도-방문번호)로만 표기, 점검자 정보는 받지 않음 |
| 점검 코드 입력 | 시도는 목록 선택, 방문번호는 숫자만 허용(센터명·성명 입력 칸 없음) |
| 자유 기재란 | 칸마다 개인정보 입력 금지 안내 표시, 전화번호·등록번호·여권번호·이메일·생년월일·호칭(○○씨/님) 형식 실시간 경고, 내보내기·출력 전 재검사 |
| 사전제출 엑셀 | 양식에 개인정보 칸이 없고, 정해진 코드의 값만 읽음(개인정보 형식 값은 버림) |
| 저장 위치 | 기기 내부 IndexedDB. 서버·클라우드 전송 없음 |
| 외부 통신 | 외부 CDN·글꼴·분석·광고·AI API 없음. CSP로 같은 주소 외 연결 차단(`connect-src 'self'`) |
| 오프라인 캐시 | 앱 파일만 캐시, 점검 기록은 캐시하지 않음 |
| 보고서 | 점검 코드만 출력, 센터명·담당자·연락처·주소·점검자 성명은 빈칸(출력 후 수기) |
| 삭제 | 자동 삭제 없음. 개별·전체 삭제 모두 확인 절차 거침 |

## 2. 남는 위험과 한계

1. **개인정보 검사의 한계**: 패턴 검사는 형식이 정해진 번호류와 일부 호칭만 찾습니다. 이름이나 특정 가능한 서술을 모두 막지 못하므로 사용자 교육이 필요합니다.
2. **공개 호스팅**: GitHub Pages는 공개 주소입니다. 앱 화면과 코드는 누구나 볼 수 있습니다(점검 기록은 포함되지 않음). 접속 기록(IP 등)은 GitHub에 남습니다.
3. **화면 비밀번호의 무의미함**: 공개 정적 사이트에서 브라우저 안 비밀번호는 코드로 우회할 수 있어 실제 접근 통제가 되지 않습니다. 그래서 두지 않았습니다. 기기 잠금이 실질적 보호 수단입니다.
4. **기기 분실·도난**: 기록은 암호화되지 않은 상태로 브라우저 저장소에 있습니다.
5. **점검 코드와 일정표**: 점검 코드는 시도 단위라 그 자체로는 센터를 특정하기 어렵지만, 점검계획 일정표와 합쳐지면 특정됩니다. 일정표는 앱·백업·PDF와 분리해 원 내부에서 관리합니다.
6. **파일 관리**: 백업(JSON)·PDF는 기기 '파일' 앱이나 클라우드 동기화(iCloud Drive 등) 대상이 될 수 있습니다. 공유폴더로 옮긴 뒤 기기 사본을 지웁니다.
7. **데이터 유실**: 브라우저 데이터 삭제·앱 삭제·장기 미사용 시 기록이 사라질 수 있습니다.
8. **코드 변경 통제**: 저장소 쓰기 권한자가 코드를 바꾸면 모든 사용자 기기에 반영됩니다. 쓰기 권한을 최소화하고 변경 이력을 검토합니다.

## 3. 시범운영 전 기관 확인 절차(권고)

1. **정보보안 담당 부서**: 본 문서, README, 소스 전체, 입력 항목 목록 제출 → 외부 호스팅 사용, 업무 기기 범위, 백업·PDF 보관 기준 확인
2. **개인정보 보호 담당자**: 개인정보 미수집 확인, 자유 기재란 운영 기준 확정
3. **소관 부서**: 점검 항목·미흡 사유·권고 문안·[행정 확인 필요] 항목 검토 → `js/config/criteria.js` 반영
4. **호스팅 결정**: 1순위 기관 내부 웹서버(정적 파일만 올리면 됨, HTTPS 필수), 2순위 기관 조직 계정 GitHub Pages
5. **사용자 교육**: 기기 잠금, 일정표 방문번호 배분, 자유 기재 금지 사항, 백업 절차
