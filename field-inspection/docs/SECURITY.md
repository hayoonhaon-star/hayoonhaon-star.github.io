# 보안 한계 및 기관 승인 절차

## 1. 설계상 보호 조치

| 구분 | 조치 |
|---|---|
| 개인정보 수집 | 이름·연락처·주소·여권·외국인등록번호·노동자 응답 입력 칸 없음. 대상은 익명 순번(방문 농가 N)으로만 표기 |
| 자유 기재란 | 결과 검토 문안·시군 건의사항에 전화번호·주민/외국인등록번호·여권번호·이메일 형식이 들어가면 저장하지 않음 |
| 식별지표(붙임5) | 개별 응답·피해 진술 저장 기능 없음. 문항 열람과 조치 절차 안내만 제공 |
| 저장 위치 | 기기 내부 IndexedDB. 서버·클라우드 전송 없음 |
| 외부 통신 | 외부 CDN·글꼴·분석·광고·AI API 없음. 콘텐츠 보안 정책(CSP)으로 같은 주소 외 연결 차단(`connect-src 'self'`) |
| 오프라인 캐시 | 앱 파일만 캐시. 점검 기록은 캐시하지 않음 |
| 전송 | 자동 동기화·메일 발송 기능 없음. PDF는 사용자가 직접 저장·전달 |
| 삭제 | 설정 화면에서 기기 기록 전체 삭제, 예시 데이터만 삭제 가능 |

## 2. 남는 위험과 한계

1. **기기 분실·도난**: 기록은 암호화되지 않은 상태로 브라우저 저장소에 있습니다. 기기 잠금(암호·생체인증)을 반드시 설정해야 합니다.
2. **번호-실명 대응표**: 앱은 익명 번호만 다루지만, 별도로 관리하는 대응표와 합쳐지면 대상이 특정됩니다. 대응표는 앱·PDF와 분리해 종이 등으로 관리합니다.
3. **자유 기재 내용**: 형식 검사로 번호류는 막지만, 이름이나 특정 가능한 서술까지 자동으로 막지는 못합니다. 사용자 교육이 필요합니다.
4. **PDF 파일 관리**: 저장된 PDF는 기기 '파일' 앱이나 클라우드 동기화(iCloud Drive 등) 대상이 될 수 있습니다. 기관 문서 관리 기준에 따라 보관·폐기합니다.
5. **데이터 유실**: 브라우저 데이터 삭제·앱 삭제·장기 미사용 시 기록이 사라질 수 있습니다. 공식 기록은 PDF와 기관 제출 자료입니다.
6. **호스팅**: GitHub Pages는 외부 상용 서비스입니다. 앱 파일 자체에는 점검 정보가 없지만, 접속 기록(IP 등)은 GitHub에 남습니다. 공개 저장소로 올리면 누구나 앱 코드를 볼 수 있습니다.
7. **코드 변경 통제**: 저장소 쓰기 권한이 있는 사람이 코드를 바꾸면 모든 사용자 기기에 반영됩니다. 쓰기 권한을 최소화하고 변경 이력을 검토합니다.

## 3. 시범운영 전 기관 승인 절차(권고)

1. **정보보안 담당 부서 사전 검토**
   - 제출 자료: 본 문서, README, 소스 파일 전체, 입력 항목 목록(개인정보 미수집 확인)
   - 검토 요청 사항: 외부 호스팅(GitHub Pages) 사용 가능 여부, 업무용 기기 사용 범위, PDF 보관 기준
2. **개인정보 보호 담당자 확인**
   - 개인정보 수집 항목 없음 확인, 자유 기재란 운영 기준 확정
3. **문항·문안 검토**
   - 소관 부서(농식품부 등)와 미준수 사유 분류·지적/권고 문안·확인 서류를 검토해 확정하고, `checklists.js` 반영
4. **호스팅 결정**
   - 1순위: 기관 내부 웹서버(정적 파일만 올리면 됨, HTTPS 필수)
   - 2순위: 기관 조직 계정의 GitHub 저장소 + Pages(비공개 저장소는 유료 플랜, 사이트 접속 제한은 Enterprise Cloud만 가능 — 그 외에는 주소를 아는 누구나 앱 화면에 접속 가능하나 점검 기록은 각 기기에만 있음)
   - 시연만 할 때: 개인 PC에서 로컬 실행(README 4절)
5. **사용자 교육**
   - 기기 잠금, 익명 번호 운영, 자유 기재 금지 사항, PDF 저장·제출·삭제 순서
6. **시범운영 종료 시**
   - 사용자별 기기 기록 삭제 확인, 저장 PDF 정리, 호스팅 중단 또는 유지 결정

- 보안성 검토(필요 시 보안 인증 대상 여부 확인) 및 개인정보 영향평가 대상 여부 검토
- 저장소 어댑터(`js/storage.js`)를 기관 서버 API로 교체
